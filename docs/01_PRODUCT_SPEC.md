# 产品规格

## 定位

构建网页端、开放对话式、可验证、可修改的全球动漫圣地巡礼旅行 Agent。

示例：

> 我从京都出发，九月去东京三天，想巡礼《孤独摇滚！》，预算中等，希望少走路，第 8 集相关场景优先。

系统从自然语言提取条件，让用户确认关键决策，组合动漫目录、可信巡礼点、长途交通、当地路线、天气和攻略知识，生成带来源的旅行计划。

## 用户链路

```text
开放式输入
→ 动态条件卡
→ Bangumi 作品候选确认
→ Route A 全量巡礼点
→ Access Plan 长途候选
→ 用户选择交通和住宿基地
→ Route B 每日可执行路线
→ Reviewer/Validator
→ 地图、时间轴、引用和外部导航
→ 自然语言局部修改
```

完整旅行层次：

1. **Access Plan**：用户所在地到目的地机场/车站；
2. **Base Plan**：住宿城市或车站区域；
3. **Pilgrimage Plan**：每日片区、点位、顺序、停留和路线。

全球旅行 Agent 与圣地巡礼并不冲突：前者解决抵达和基地，后者解决目的地内的主题路线。

## Mixed-Initiative 交互

自由对话之后展示可编辑条件卡。以下内容不能静默猜测：

- Bangumi 作品；
- 出发地、目的地、旅行日期；
- 航班或城际交通；
- 住宿基地；
- 必去与排除点；
- 任何付款、预订或不可逆操作。

默认值可以推荐，但必须可见、可编辑并说明来源。

## Route A 与 Route B

### Route A

Route A 是经清洗、去重、坐标校验并保留来源的全部候选巡礼点。不得因用户时间不足而删除，也不得由 LLM 编造。

### Route B

Route B 只能从 Route A 选择，是满足当前旅行约束的子集和顺序。约束包括日期、交通抵离、基地、每日时间窗、必去/排除、步行、天气、访问和礼仪。

未选点仍显示，并提供结构化原因：时间不足、过远、用户排除、天气/访问冲突、低优先级或无法可靠验证。

## 页面要求

- 对话区和条件卡；
- 作品候选；
- 交通候选卡：推荐、最快、最低价格、最少中转；
- Route A/Route B 地图切换和来源图例；
- 每日时间轴、Reviewer 警告、未选原因；
- Google Maps 小路线按钮；
- 数据状态：实时、缓存、估算、社区经验、需确认；
- 自然语言修改和计划版本；
- JSON、GeoJSON、可打印 HTML 导出；
- 响应式、错误、空状态和降级体验。

## MVP 非目标

- 自动付款、出票、酒店预订；
- 全球铁路实时聚合，第一版使用人工/规则 Provider；
- 相机叠影、照片归档、原生移动 App；
- 自动批量抓取社区平台或绕过访问保护；
- 复杂社交与生产级商业运营。
